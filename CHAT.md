Отличная и вполне реализуемая идея — по сути "где сейчас мой автобус" вместо "во сколько по расписанию". Хорошая новость: тебе не придётся парсить сырые GPS-данные автобусов вручную — для Берлина есть готовые источники данных.

Источники данных, от простого к сложному:

v6.bvg.transport.rest — бесплатный REST-обёртка над HAFAS API BVG, без авторизации, лимит 100 req/min. Для твоей задачи там есть ровно то что нужно:
/trips/{tripId} — возвращает все остановки конкретного рейса с реальным (не плановым) временем прибытия/отправления. По этому списку легко определить "последнюю пройденную остановку" — берёшь stopovers, у которых departure.when уже в прошлом, последний такой = откуда автобус выехал.
/radar?north=...&west=...&south=...&east=... — отдаёт все транспортные средства в bounding box с их текущим движением. Это буквально "радар автобусов" — можно сразу получить позиции без пляски с trip ID.
/stops/{id}/departures — чтобы для начала найти tripId нужного автобуса на нужной линии.
Официальный GTFS-RT от VBB (https://production.gtfsrt.vbb.de) — protobuf-фиды VehiclePositions/TripUpdates/ServiceAlerts, официальный источник, на котором построен сам HAFAS. Более "правильный" с точки зрения архитектуры (это тот же формат, что использует Google Maps/Transit), но требует парсинга protobuf (gtfs-realtime-bindings есть под Java) и статических GTFS-данных (расписание, остановки, шейпы) для сопоставления.

Для пет-проекта я бы начал с bvg.transport.rest, а не с сырого GTFS-RT — там уже готовый JSON, ничего парсить не надо, и /radar закрывает 80% задачи одним эндпоинтом.

Как определить "последнюю пройденную остановку":

Берёшь stopovers из /trips/{id} — там для каждой остановки маршрута есть plannedDeparture и departure (реальное время, с задержкой). Сравниваешь departure.when с текущим временем — последняя остановка, у которой departure уже в прошлом, и есть "откуда автобус выехал". Дальше можно интерполировать позицию между этой и следующей остановкой по времени, если хочется анимации на карте, а не просто текста "выехал с Х".

MVP, который реально можно сделать за вечер-два:

Захардкодить линию + список остановок, которые тебя интересуют (например, твой маршрут до дома).
Cron/scheduler раз в 20-30 сек дёргает /departures для нужной остановки → берёт tripId ближайшего автобуса → дёргает /trips/{id} → вычисляет последнюю пройденную остановку.
Отдаёшь через свой мини-эндпоинт на фронт: "автобус 140 выехал с Х 2 минуты назад, ETA до тебя ~4 мин".

Учитывая, что ты уже строил multi-agent housing search с Claude Code CLI, cron collection job и т.д. — по стеку это будет плюс-минус тот же паттерн: Java/Spring Boot сервис + периодический polling + простое хранилище + отдача на фронт.

Одна тонкость: HAFAS (на котором построен bvg.transport.rest) не всегда даёт GPS-координаты транспортного средства напрямую в /trips — но /radar их даёт. Если хочешь именно точку на карте (а не "между остановками"), лучше сразу ориентироваться на /radar с bounding box вокруг твоего маршрута — так проще, чем вычислять интерполяцию вручную.

Короткий честный ответ: зависит от того, что именно ты спрашиваешь у API.

Дискретные события ("выехал с остановки X в Y:ZZ") — довольно надёжны. Данные приходят от бортового RBL/ITCS-компьютера автобуса, который детектирует прибытие/отправление на каждой остановке (обычно по GPS-геозоне или одометру) и шлёт это в центральную систему BVG. Это конкретное измеренное событие, а не расчёт — именно поэтому твоя идея "последняя пройденная остановка" методологически сильнее, чем попытка получить живую точку на карте.

Непрерывная позиция между остановками — намного слабее. Нашёл прямое подтверждение от людей, разбиравших BVG Live-карту: она не использует прямые GPS-данные, а грубо интерполирует движение между двумя известными точками на основе расписания — отсюда рывки/резкие остановки на карте, и если для конкретного рейса нет real-time данных, карта тихо откатывается на "по расписанию", не сообщая об этом явно.

Практические следствия для твоего проекта:

Бывают дыры в покрытии. Не все автобусы всегда шлют real-time — если данных нет, departure.when может совпадать с plannedWhen (т.е. это не реальное время, а расписание, замаскированное под реальное). Стоит явно сверять when vs plannedWhen/delay и помечать в UI, если delay отсутствует — значит, данные не факт, а прогноз.
Задержки на кольцевых/конечных остановках иногда учитываются с лагом в минуту-две — источник не миллисекундный трекер, а система с интервалом обновления.
Для "жду ли я автобус зря" это всё равно значительно лучше голого расписания — задержки 5-15 минут (характерные для "автобусы ходят как попало") RBL-система ловит корректно, просто не жди точности "автобус в 200 метрах от остановки".

Если хочешь для себя оценить реальную точность на своём маршруте — самый быстрый способ: погонять /departures и /trips для знакомой линии в течение недели и сравнить delay с тем, что видишь глазами на остановке. Это даст тебе эмпирическую погрешность именно для твоих автобусов, а не общие рассуждения.
